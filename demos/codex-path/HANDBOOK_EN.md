# Learn Codex: Zero to Pro handbook (independent)

> Independent educational handbook / tài liệu học tập độc lập. Not an official OpenAI certification.
> Editorial version: 2026-10-25. Source index: 2026-10-24. Features may differ by account and change.

Start without knowing how to code. Choose a small task, use fictional data, review it, then progress.

## Start in three steps

1. Choose who you are: student, teacher, office worker, creator, developer or first-time user.
2. Draft a synthetic-data prompt, try it in a tool you already have and review its result.
3. Check uncertain claims, then continue with a short hands-on lesson.

Open [Three-minute starter](https://codex.xuanhieu.org/demos/codex-path/#start) and [Interactive guide](https://codex.xuanhieu.org/demos/codex-path/#guide).

## Five learning levels

| Tier | Learning outcome |
|---|---|
| Zero | Create one bounded brief and verify sources. |
| Beginner | Build one small example with source and rollback notes. |
| Intermediate | Produce a repeatable contract, tests and checklist. |
| Advanced | Simulate gated approvals and independent QA. |
| Pro | Publish a reproducible source package and release evidence. |

## 19 concepts: understand → try → verify

### 1. What can AI do for me? (Zero)

**In plain language:** AI helps you draft, explain and organize tasks. You decide the goal and review the result before using it.

**Everyday analogy:** Like asking a helper for a first draft: the draft does not make decisions for you.

**Worked example:** Example: ask for a fictional seven-day, ten-minute study plan, then adjust it yourself.

**Common mistake:** Treating plausible text as verified truth; entering secrets or private details.

**Quick exercise:** List three small tasks, choose one and make a draft marked 'needs verification'.

### 2. ChatGPT, Work or Codex? (Zero)

**In plain language:** ChatGPT suits explanations and drafting. Work handles multi-step deliverables. Codex works on software projects, reviews changes and tests; access depends on your account.

**Everyday analogy:** Pick the right tool: writing a draft does not require a software workshop.

**Worked example:** Drafting an invitation? Start with ChatGPT. Multi-file deliverables? Consider Work. Fixing code and running tests? Use Codex with permission.

**Common mistake:** Assuming every AI task requires an API key or programming skill.

**Quick exercise:** List five everyday tasks and choose a tool for each with a reason.

### 3. How to write a clear request (Zero)

**In plain language:** A good request gives the task, audience, safe example input and review criteria. No special jargon is needed.

**Everyday analogy:** Like a short work order: state the goal, constraints and definition of done.

**Worked example:** 'Give five games for middle-school students, one sentence each, no expensive equipment; flag safety checks before use.'

**Common mistake:** Writing only 'make it better' and expecting a precise outcome.

**Quick exercise:** Write a four-part prompt, try it with fictional details and revise one ambiguous point.

### 4. Protect your private information (Zero)

**In plain language:** Never put passwords, API keys, identifying images or other people's private data in public lessons. Practice with fictional examples and approve high-impact actions first.

**Everyday analogy:** Like mailing a postcard: once shared it can be copied, so inspect it first.

**Worked example:** Replace a real address with 'Example Street', an email with example.invalid and a token with SAMPLE_ONLY.

**Common mistake:** Assuming a small blur or a hidden UI element fully protects original files.

**Quick exercise:** Review a demo screenshot and identify five spots that might expose private details.

### 5. AI can be wrong. How do I check? (Zero)

**In plain language:** Fluent text is not evidence. Separate verifiable claims, those requiring official sources, and suggestions.

**Everyday analogy:** Like checking a math result: a neat answer still needs verification.

**Worked example:** A claim that a service is free for everyone may have changed; check the current plan page before repeating it.

**Common mistake:** Copying results without checking references, date or limitations.

**Quick exercise:** Classify three fictional claims as sourced / unverified / opinion.

### 6. Your first safe Codex task (Beginner)

**In plain language:** Codex works on software tasks within a project. Start in an available client; before edits, specify a sandbox folder, goal, forbidden actions and verification.

**Everyday analogy:** Like hiring help for one chair: access should not extend to the rest of the house.

**Worked example:** 'In the demo folder, fix the Search button label. Do not delete or deploy. Show a diff and mobile checks; report PASS only after running them.'

**Common mistake:** Granting broad permissions to private folders or publishing without reviewing the diff.

**Quick exercise:** Write a fictional change brief with sandbox scope, three tests and rollback.

### 7. What are Git, repos, commits and diffs? (Beginner)

**In plain language:** A repo tracks project history. A commit is a saved milestone. A diff shows changes. Understanding these prevents accidental loss.

**Everyday analogy:** Like a notebook photographed after each revision.

**Worked example:** Change 'Hello' to 'Welcome' in a sample file and compare the before/after diff.

**Common mistake:** Believing pressing Save automatically creates a Git commit or backup.

**Quick exercise:** Create a three-column before/after/reason table with rollback.

### 8. How to tell whether a change works (Beginner)

**In plain language:** A test compares observed results against expectations. Cover normal, invalid input, small screens and undo, not just appearance.

**Everyday analogy:** Like checking a lock: actually test the door, not only the key.

**Worked example:** An email form should clearly handle empty, invalid and valid input.

**Common mistake:** Calling a visually attractive page fully tested without exercising it.

**Quick exercise:** Write five test cases: 'Action → Expected → Observed'.

### 10. Why do agents need bounded instructions? (Intermediate)

**In plain language:** AGENTS.md can hold project-specific instructions and test commands. Keep them brief, scoped and explicit about required approvals.

**Everyday analogy:** Like lab rules: everyone knows what equipment they may use.

**Worked example:** Example AGENTS.md: 'Edit src/demo only; run npm test; never read .env; don't deploy production'.

**Common mistake:** Writing huge or contradictory rules that block necessary work.

**Quick exercise:** Draft a six-line AGENTS.md for a sample project.

### 11. Package a reusable workflow (Intermediate)

**In plain language:** A reusable skill needs a goal, input, steps, constraints and an acceptance test. Start with a manual task you've already validated.

**Common mistake:** Collecting dozens of unknown scripts and trusting them without inspection.

### 12. Parallel work without merge collisions (Intermediate)

**In plain language:** A Git worktree is a separate working folder for a branch. Define tasks, file ownership and integration before using multiple agents.

**Everyday analogy:** Like teams renovating separate rooms, not editing the same wall concurrently.

**Worked example:** Agent A writes tests, Agent B builds UI, a reviewer checks the merged branch and records issues.

**Common mistake:** Letting multiple agents edit the same production folder or file without coordination.

**Quick exercise:** Sketch three roles, three folders and a tested merge step.

### 13. Connecting tools with least privilege (Intermediate)

**In plain language:** External connections may read or modify data; grant only necessary permissions, prefer read-only trials and disconnect unused integrations.

**Everyday analogy:** Like lending a key to one room, not the entire building.

**Worked example:** Connect a synthetic read-only document source, list files and verify no delete action is available.

**Common mistake:** Publishing an all-access API token in code or granting access to every file.

**Quick exercise:** Build a table: integration → minimal permission → approver → revocation.

### 14. Pause before high-impact actions (Advanced)

**In plain language:** Reading and modifying files are different privileges. Deletions, data sends and purchases need authorized approval.

**Everyday analogy:** Like a warehouse requiring a manager's sign-off before dispatch.

**Worked example:** An agent requests to send an email: pause, record an approver and continue only if authorized.

**Common mistake:** Confusing agent autonomy with the right to override permissions.

**Quick exercise:** Simulate Allow/Review/Stop decisions for five scenarios.

### 15. Multi-agent work with clear ownership (Advanced)

**In plain language:** Multiple agents help when tasks are separable, with file boundaries and evidence review. A small task may be better with one agent.

**Worked example:** Planner briefs, Builder changes a sandbox, QA independently tests; merge only with evidence.

**Common mistake:** Counting agents as the KPI without final accountability.

### 16. Ship updates without breaking production (Advanced)

**In plain language:** A release gate checks tests, private data, content and rollback before publishing. Production needs a way back.

**Everyday analogy:** Like a preflight checklist: missing a critical item blocks takeoff.

**Worked example:** If a file contains an obvious token, the gate must FAIL and avoid upload.

**Common mistake:** Checking build success alone without user flows or privacy.

**Quick exercise:** Write eight PASS/FAIL checks and test one blocking failure.

### 18. Evaluate agents with reproducible cases (Pro)

**In plain language:** Measure quality using reproducible inputs, expected results and observed outputs. Count missed errors and false alarms; do not extrapolate from a demo.

**Everyday analogy:** Like a test with an answer key and an agreed rubric.

**Worked example:** Run ten synthetic scenarios, record PASS/FAIL and inspect two errors.

**Common mistake:** Claiming 99% accuracy from a few handpicked prompts.

**Quick exercise:** Create ten varied cases and a brief error review.
